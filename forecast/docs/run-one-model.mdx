The supported publisher interface is `meteo forecast build`, the CLI
`@azohra/meteo.forecast` installs (`pnpm exec meteo forecast build`).
Model-specific builder modules
remain implementation details; downstream automation should use
the CLI so external site and output paths are scoped consistently.

<Steps>

1. **Confirm the model declaration.** Read [Choose models](/docs/forecast/choosing-models/)
   and [Model capabilities](/docs/forecast/model-capabilities/). The slug in
   `models.json` is its identity.
2. **Preflight paths and selection.** This performs no network access or
   writes:

   ```sh title="Terminal"
   pnpm exec meteo forecast build --model hrrr-conus --sites ./sites.json --output ./public/data --dry-run
   ```

   Success is one line, `Would build hrrr-conus for N site(s) from … into …`,
   with both paths resolved absolute and nothing written.

3. **Use a short smoke cap when appropriate.** Append `--max-steps 2` to the
   dry run to select the first two scheduled steps; it limits forecast
   steps, not sites or fields.
4. **Point the engine at your published root.** A real build (never the dry
   run) reads the published dataset to detect what is already there, and
   refuses to guess where that is: without configuration it exits with
   `PublisherConfigurationError`. Set `METEO_DATA_BASE` to the public URL
   your dataset will live at — on day one, before anything is published
   there, that URL 404s and the engine correctly treats it as "nothing
   published yet" and builds everything:

   ```sh title="Terminal"
   export METEO_DATA_BASE="https://forecasts.your.club/data"
   ```

   Deployments that read their bucket directly instead leave it unset and
   provide the R2 credential set (`METEO_R2_BUCKET`, `R2_ENDPOINT`,
   `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`).
5. **Run the build.** Remove `--dry-run` (and `--max-steps`, if you used
   it) for the full declared horizon.
6. **Inspect output before deploying it.** The model manifest and each
   expected site profile must share the same `referenceTime`; one line of
   output means they do:

   ```sh title="Terminal"
   jq -r '.referenceTime // .run.referenceTime' public/data/hrrr-conus/manifest.json public/data/hrrr-conus/sites/*.json | sort -u
   ```

   For byte-level validation, parse each file with the raw-text guards from
   [`@azohra/meteo.briefing/contract`](/docs/briefing/contract/) — the same
   check every consumer runs.

</Steps>

## Complete command surface

```text
meteo forecast build (--model SLUG | --all) --sites PATH
               [--output PATH]
               [--max-steps N]
               [--history | --no-history]
               [--dry-run]

meteo forecast terrain --sites PATH [--output PATH]

meteo forecast runs-index [--output PATH]

meteo forecast freshness --model SLUG --manifest PATH

meteo forecast catalogue [--output PATH]
```

A site catalogue is required (`--sites` or `METEO_SITES`); which sites an
operator publishes is their decision, so there is no default. The output
root defaults to `./data`. `--model` and `--all` are mutually exclusive.
Unknown model slugs, missing or unreadable site files, invalid site
catalogues, and unusable output paths fail with an actionable error.

History publication is the operator's flag, on by default: every
successful build also appends
the [append-only month archives](/docs/briefing/history-archives/) and their sidecar
indexes. `--no-history` publishes current documents only.

`terrain` regenerates
[`site-context.json`](/docs/briefing/site-context-document/);
`runs-index` regenerates `runs.json` wholesale from the published
manifests; `freshness` prints exactly `fresh` or `stale` so an upload flow
can refuse to publish backwards; `catalogue` emits the packaged
`models.json`. Teaching-scenario generation is source-checkout tooling,
not engine surface.

<Aside type="caution" title="A full build is a data job">
  Builders fetch real provider files. Whole-domain ECCC deterministic runs can
  move several GiB; ensembles can move substantially more. NOAA builders use
  indexed byte ranges but still fetch many records. Per-model transfer costs
  are recorded in the
  [forecast feed reference](/docs/forecast/forecast-model-feeds/). Do not
  remove a smoke cap casually or schedule a model more often than it
  publishes.
</Aside>

Each builder detects the latest complete provider run and exits without
rewriting output when that `referenceTime` is already published. "Already
published" is read from the published dataset itself, at the root step 4
configured, and the same source seeds
the month archives that history appends continue. A successful
new run writes current profiles, appends history, and writes the model
manifest. [Environment and credentials](/docs/forecast/environment/) is the
complete variable list. [Schedule builds](/docs/forecast/schedule-builds/)
applies the catalogued publication cadence to recurring jobs.

## When a build fails

A build fails loudly rather than publishing a wrong document. The errors
you will actually see: a missing or non-finite required sample throws
`` `${provider} returned no ${fieldName} for ${site.name}` ``; a NaN that
survives to publication is refused by the shared writer with
`` `non-finite value ${value} at ${path} — refusing to publish` ``; a site
outside the model's sampling guard fails with an out-of-grid error; and a
real build without a configured published root exits with
`PublisherConfigurationError` (step 4). A failed build exits non-zero
before the deploy step your scheduler gates on
([Schedule builds](/docs/forecast/schedule-builds/)), so the previous
publication stays live and the next tick simply tries again.

## Render what you built

Rendering is the read side's job, and
[Render a first Meteogram](/docs/briefing/render-first-meteogram/) is the
complete walkthrough — fetch, validate, scene, SVG. Point its `base` at
your own published root (the same URL as `METEO_DATA_BASE`) instead of the
sample dataset, and use your own model and site slugs. When the page loads
a manifest and profile pair from cached static storage, use `loadForecast()`
from [`@azohra/meteo.briefing/transport`](/docs/briefing/transport/) so the
pair is guaranteed to describe one model run.

Before that URL exists, the same walkthrough runs unchanged against the
built directory: serve `--output` locally
(`npx serve public/data`, or any static file server) and point `base` at it.
