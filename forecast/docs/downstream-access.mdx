meteo by Azohra ends at inspectable static artifacts and reusable rendering tools.
Authentication, membership, launch discovery, product navigation, alerts,
retention, and operational language belong to the downstream application.

## Choose access at the hosting boundary

| Publication need | Downstream implementation |
| --- | --- |
| Public club archive | Static host or object storage with explicit retention |
| Member-only current output | Application or edge authorization in front of the static tree |
| Build-time chart pages | Fetch/validate during the downstream build and deploy generated HTML/SVG |
| Custom interactive viewer | Validate documents, build a scene, and own browser state and accessibility |

The JSON contract does not contain users, roles, sessions, launch permissions,
or API keys. Adding them would couple portable forecast documents to one
publisher's policy.

Hosts that address the tree by key rather than by URL (object storage
behind an application, a Cloudflare Worker reading an R2 bucket binding)
should build those keys with
[`documentPaths`](/docs/briefing/transport/#the-trees-layout-is-exported)
from `@azohra/meteo.briefing/transport`, the published tree's exported path
layout. It returns each document's root-relative path (the loaders fetch
`${baseUrl}/${documentPaths...}`), so a gate or edge function keys its
reads from the exported layout instead of hand-writing it a second
time.

Whatever the host, serve the bytes as published. Documents keep
`application/json`; `.jsonl.gz` history archives keep `application/gzip`,
or go out as raw gzip bytes with no `Content-Encoding` header, so a reader
receives the archive itself, never a transparently decompressed body. Let
`Cache-Control` be short on manifests and current documents, which change with
every publish; [history archives](/docs/briefing/history-archives/) are
append-only, so the current month's archive changes with each new run and a
closed month's does not — those can cache long.

## Read independently cached files safely

Static storage can expose a new manifest before the matching profile cache
entry expires, or the reverse. TypeScript consumers should use
`loadForecast()` from `@azohra/meteo.briefing/transport`, which returns a run-consistent
pair, a pair flagged `stale`, or a discriminated miss; the
[transport guide](/docs/briefing/transport/) defines that contract.
Consumers own caching, credentials, fallback selection, and stale-state
presentation.

At every access level, keep provider attribution with derived material and
state the publisher's operational limitations.

[Render a first Meteogram](/docs/briefing/render-first-meteogram/) run
against your published root ends with static files that can be copied
byte-for-byte to any of these downstream boundaries. No meteo process
remains running after generation.
